Overview

Keeps a journal of who worked on which sales order and when, so a sales manager can see the activity of each salesperson per day.

One activity record per order, user and day. The first time an internal user touches a sales order on a given day, an activity record is created for that order, user and date; later actions of the same user on the same day are added to it. Actions of the system and of portal or website users are not recorded.

What is recorded. The Log tab of a record holds the timed list of:

  • ✓
    field changes, with the old and the new value (order lines are described line by line);
  • ✓
    the Confirm, Cancel, Set to Quotation, Lock, Unlock and Send buttons;
  • ✓
    messages posted in the chatter.

Scheduling an activity on the order also creates the record of the day, without a log line. The record keeps the order status, and the flags Chatter Message and Tags Changed. Binary fields (labels, signatures) are not logged, and long values are truncated.

Activity Records report. Sales > Reporting > Activity Records opens the records of the current month in list, form, pivot (users and stages per day) and graph views, with Today, Yesterday, This Month and This Year filters and grouping by user, stage or date.

Access. User: Own Documents Only salespeople can read the records of their own orders and of unassigned ones; User: All Documents and Administrator see all of them, within their allowed companies. Only the Sales Administrator can change or delete records. The Reporting menu of Sales, and so the report, is shown to the Sales Administrator only.

Automatic clean-up. A Data Cleaning rule deletes the records older than 2 months. The period can be changed in Data Cleaning > Configuration > Rules > Recycle Records, rule Sale Order Activity Record.

With order stages. When the order stages from deltatech_website_sale_status are installed, the record also keeps the order stage and the AWB Generated flag, set when the order moves to Pre advice.

Versions

19.0.1.2.2 (2026-11-03)

  • Summary corrected: the module keeps a separate activity journal per order, user and day, not a "last modified" field on the order.
  • Description rewritten after the code: what is logged (field changes, header buttons, chatter messages, scheduled activities), the Activity Records report and its views, the access rules, the Data Cleaning rule and the optional order stages.
  • Apps banner aligned with the description.

19.0.1.2.1 (2026-10-22)

  • Listed on Odoo Apps as Sale Activity Log (was Sale Order Last Modified). The technical name deltatech_sale_activity_report does not change.

19.0.1.2.0 (2026-10-09)

Fix — scheduling an activity on a sale order no longer fails when deltatech_website_sale_status is not installed: the order stage is copied into the journal only when the field exists (ACTIVITY-001).

Fix — the activity journal follows the access scope of sale orders (ACTIVITY-002):

  • salespeople see only the journal of their own orders (or unassigned ones), "All Documents" salespeople and managers see all, always limited to the allowed companies;
  • salespeople can only read the journal; only the Sales Administrator can edit or delete entries; internal users without sales rights have no access;
  • entries keep being written automatically, by the system, for every user.

19.0.1.1.2 (2026-09-29)

  • Own module icon, instead of the generic gears it had.

19.0.1.1.1 (2026-08-24)

Fix — logging no longer fails when an order line that is not saved yet is deleted from the form.

The web client refers to unsaved lines through virtual ids (virtual_7149). The description of the commands on order_line read this id as if it were one from the database, and the operation ended with Expected singleton — the log of the whole write was lost, including the legitimate changes made at the same time, and a traceback was left in the log at every save of this kind.

Now the ids that are not numeric are displayed as text, and a line deleted in the meantime is reported by id, without being read from the database anymore.

19.0.1.1.0 (2026-08-15)

Fix — the activity log no longer stores the content of binary fields.

Changing a binary field of the order (the AWB label, the signature) wrote into activity_log the whole base64 content of the file. The same problem inflated a customer's database by 1.7 GB through the equivalent module for transfers; here the measure is preventive — at the current scale the order log stays small, but sale.order has the same binary fields.

Now:

  • binary fields are ignored completely when logging — they are no longer even read from the filestore, so writing on the order is even faster;
  • the logged field values are truncated to 200 characters (2000 for x2many fields, described line by line), with the number of truncated characters marked;
  • the chatter messages are truncated to 2000 characters;
  • the log of one day is capped at 64 kB, keeping the recent activity.
