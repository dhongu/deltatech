Moves goods between two warehouses in two steps, through a transit
location: the sending warehouse ships the goods to transit, and the
receiving warehouse gets its own transfer, with the same products, from
transit to its stock.

**Operation types for the two steps.** On an internal operation type you
set **Two Step Transfer Use**: *Delivery* for the transfer that sends
the goods to the transit location, *Reception* for the transfer that
brings them from transit into the receiving warehouse.

**Create Transfer button.** On an internal transfer whose operation type
is marked *Delivery* and that has no **Source Document**, the **Create
Transfer** button opens a wizard where you choose the reception
**Operation Type**. The module creates and confirms the second transfer,
from the destination of the first transfer to the default destination of
the chosen operation type, with the same products and quantities. Each
transfer gets the address of the other warehouse as contact, and both
are linked by chatter messages. The button disappears once the second
transfer exists.

**Automatic second transfer.** When **Auto Second Transfer** is checked
on the *Delivery* operation type, the second transfer is created when
the first one is validated, without the wizard. The receiving warehouse
is the one whose **Address** is the **Contact** of the transfer, and its
internal operation type marked *Reception* is used. Transfers with a
**Source Document** (replenishment, sale orders) are skipped, since
their receiving transfer already exists.

**Checks on reception.** The second transfer can be validated only with
products that come from the first transfer or its backorders. A
backorder of the first transfer does not create another second transfer:
a chatter message tells which transfer will receive its products.

**Reassign Location (optional).** When the system parameter
``deltatech_picking_transit.use_sub_locations`` is set, internal
transfers show a **Reassign Location** button that sets, on each
detailed operation, the first sublocation of the source location that
has the product in stock.

Configuration
-------------

1. Create a transit location and, in *Inventory > Configuration >
   Warehouse Management > Operations Types*, an internal operation type
   in the sending warehouse with the transit location as default
   destination. Set **Two Step Transfer Use** to *Delivery* and, if you
   want, check **Auto Second Transfer**.
2. In the receiving warehouse, create an internal operation type with
   the transit location as default source and set **Two Step Transfer
   Use** to *Reception*.
3. For the automatic mode, fill in the **Address** of each warehouse and
   use it as **Contact** on the delivery transfer.

Limitations
-----------

- The first transfer stays editable after the second transfer is
  created; changes are not copied to the second transfer.

Changelog
=========

19.0.0.0.16 (2026-11-03)
------------------------

- Description rewritten from the code: the operation type field is Two
  Step Transfer Use (Delivery / Reception), not "next operation"; the
  original transfer is not locked after the second one is created.
- Documented the checks on reception, the backorder handling and the
  optional Reassign Location button.
- Summary and banner corrected.

19.0.0.0.15 (2026-10-17)
------------------------

- Fix TRANSIT-003 (#3413): opening or reloading a transit delivery no
  longer locks or unlocks it. The "Transit Transfer" indicator used to
  toggle the lock each time it was computed, so the lock state of the
  transfer depended on how often it was displayed; the lock is now
  changed only with the native Lock / Unlock button.

19.0.0.0.14 (2026-10-09)
------------------------

- Fix partial deliveries with a backorder (TRANSIT-004): the receiving
  leg checks its products against the source transfer and all its
  backorders, so the products left for a source backorder can still be
  received. A source backorder created by the native
  ``_create_backorder`` keeps "Second Transfer Created" (its products
  are already in the receiving leg, no duplicate reception) and its
  chatter names the receiving transfer.

19.0.0.0.13 (2026-10-09)
------------------------

- Apps Store banner (banner.json).

19.0.0.0.12 (2026-10-02)
------------------------

- Port the 18.0 fix: the second transfer is created with ``sudo()``
  (warehouse and reception type lookup, picking creation, move copy), so
  an operator without access rights on the receiving warehouse can
  validate the first leg.

19.0.0.0.11 (2026-10-01)
------------------------

- Fix creation of the second transfer: the removed
  ``move_ids_without_package`` field is replaced by ``move_ids``
  (TRANSIT-001).
- Fix the computed fields ``is_transit_transfer`` and
  ``sub_location_existent`` on multi-record sets (TRANSIT-002).
- Replace the commented-out tests with working Odoo 19 tests.

19.0.0.0.10 (2026-09-29)

- Own module icon, instead of the generic gears it had.
